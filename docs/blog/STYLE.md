# 블로그 글쓰기 지침

이 파일은 블로그 글 자동 생성(CONVENTIONS §13)에서 AI에게 주는 지침이다. 사람이 읽고 고쳐도 된다.

- 기준 문체: 한국어 개발 블로그의 학습 기록체. [hudi.blog](https://hudi.blog/)의 글 다섯 편(Bulkhead 패턴, MySQL 정렬, Redlock, 안정 해시, 이모지)을 분석해 공통 습관을 뽑았다 (2026-10-13).
- **문장을 베끼지 않는다.** 가져오는 것은 글의 구조와 습관이지 특정 문장이 아니다. 내용은 항상 이 저장소의 원문 문서에서만 가져온다.
- 원작자 본인의 글이 쌓이면 그 글들을 기준 문체에 추가한다.

## 1. 문장

- 종결은 평서형 `~다`를 쓴다: `~이다`, `~했다`, `~할 것이다`, `~라고 할 수 있다`.
- 독자를 끌고 가는 제안형을 섞는다: `~해보자`, `~알아보자`, `~하자`.
- 존댓말(`~습니다`, `~해요`)은 쓰지 않는다.
- 문장은 짧게. 한 문단은 2~4문장. 강조하고 싶은 한 문장은 단독 문단으로 둔다.
- 1인칭은 내가 실제로 겪은 일과 판단에만 쓴다: "나는 ~라고 판단했다", "내 실수였다". 개념 설명에서는 1인칭을 빼고 "~해보자"로 독자와 함께 간다.
- 다음 내용으로 넘어갈 때 질문을 던진다: "왜 이런 일이 생겼을까?", "그렇다면 서버가 하나 추가되면 어떻게 될까?"
- 자주 쓰는 연결어: `그렇다면`, `즉,`, `따라서`, `하지만`, `그런데`, `자, 이제`, `앞서 살펴본 것처럼`, `단,`(트레이드오프를 짚을 때).
- 핵심을 다시 말할 때 `즉,`으로 시작하는 한 문장으로 정리한다.
- 용어는 처음 나올 때 한국어와 영어를 같이 쓴다: "정족수(Quorum)", "해시 링(Hash Ring)". 이후로는 한쪽만.
- 괄호로 보충한다: "(정확히는 ~이다)".
- 담백하게 쓴다. 감탄, 과장, 홍보 말투를 쓰지 않는다. 가끔 짧은 평가는 괜찮다: "꽤 곤란한 일이다."

## 2. 글의 흐름

글 종류에 따라 아래 흐름 중 하나를 따른다.

**트러블슈팅 (원문: docs/troubleshooting/)**

```
겪은 상황을 짧게 → 증상 (로그·응답 그대로) → "왜 이런 일이 생겼을까?"
→ 의심한 것들과 하나씩 배제한 과정 → 원인과 근거 (공식 문서·소스 인용)
→ 해결과 다른 선택지를 고르지 않은 이유 → 다시 생기지 않게 한 장치 → 배운 점
```

**설계 결정 (원문: docs/adr/)**

```
어떤 문제를 풀어야 했나 → 처음 떠올린 단순한 방법과 그 한계
→ 검토한 대안 비교 (표) → 고른 방법과 포기한 것 → 검증 결과 → 다시 검토할 조건
```

**실험 결과 (원문: 실험 결과 문서)**

```
궁금했던 질문 → 예상 ("~할 것이다") → 실험 조건 → 결과 (표·그래프)
→ 예상과 달랐던 점과 이유 → 한계 (측정 환경의 제약) → 정리
```

공통:

- 도입부는 2~3문장. 내가 무엇을 하다가 이 문제를 만났는지, 왜 이 글을 쓰는지.
- 코드나 결과를 보여주기 전에 무엇을 볼지 한 문장으로 예고한다 ("아래와 같이 재현해보자"). 보여준 뒤에는 "위 결과를 보면"으로 해석한다.
- 실험이나 재현은 **예상 → 결과 → 설명** 순서로 쓴다.
- 마지막은 거창한 결론 섹션 대신 짧은 정리 한두 문단 + 실천 문장("~할 때는 반드시 ~하자").
- 끝에 `참고` 목록: 공식 문서와 원문 문서 링크. 각 항목은 제목과 링크만.

## 3. 서식

- 제목 계층은 `##`, `###` 두 단계까지. 제목은 주장이나 질문 형태도 좋다: "MySQL은 정렬을 보장하지 않는다".
- **볼드는 처음 정의하는 용어와 핵심 결론에만.** 한 문단에 하나 이하.
- 목록은 조건·전제·결과를 나열할 때만. 설명을 목록으로 쪼개지 않는다.
- 표는 비교할 때만 (대안 비교, 전후 비교, O/X).
- 코드 블록과 결과 블록은 적극적으로 쓴다. 결과는 실제 출력 그대로.
- 인용(`>`)은 공식 문서 문장을 인용할 때와 짧은 개인 의견 메모에만.
- 이모지는 쓰지 않는다.
- 긴 대시(—)를 쓰지 않는다. 쉼표나 문장 분리로 대신한다.

## 4. 그림

기준 블로그는 개념마다 그림을 두고 본문에서 "위 그림처럼"으로 가리킨다.

- 스타일: **손으로 그린 듯한 다이어그램.** 흰 배경, 검은 선, 파스텔 색 도형(파란 원, 노란 사각형), 강조는 빨간색 하나, 점선 화살표, 작은 손글씨 라벨, 사라진 것은 빨간 X.
- 개념이 바뀔 때마다 그림 하나. 상태 변화는 "변경 전 → 변경 후" 그림 두 장으로.
- 그림 바로 아래 짧은 캡션. 외부 그림을 쓰면 `출처:` 표기.
- 구현 방법은 CONVENTIONS §13 "그림"을 따른다.

## 5. 쓰지 않는 것 (AI가 쓴 티)

- 서론의 일반론 ("오늘날 클라우드 환경에서는...")
- "~하는 것이 중요합니다", "~를 살펴보겠습니다" 같은 안내 방송 말투
- "X가 아니라 Y다", "단순히 ~이 아니라" 패턴의 반복
- 같은 내용을 섹션마다 반복하는 요약
- 볼드 남발, 이모지, 긴 대시, 체크 표시, 화살표 기호 남발
- 원문에 없는 수치, 원문에서 [가설]인 내용을 확정처럼 쓰는 것
- "결론적으로", "요약하자면"으로 시작하는 마무리
